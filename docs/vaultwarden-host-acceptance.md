# Vaultwarden projection — native Wayland host acceptance

**Target-host acceptance: partial, not yet release-passed.** The user has now verified the opt-in Vaultwarden picker on the actual EndeavourOS/Hyprland desktop, including read-only sync, local GUI unlock, populated search, credential copying, and cached session reuse on a second launch. This does **not** establish logout/lock, clipboard-history, forced offline/failed-refresh, automatic theme-transition, or reversible default-cutover acceptance. All security-edge tests continue to require synthetic accounts. The historical default picker must remain usable.

## Fixture isolation before every test

- For all **remaining security and edge-case acceptance**, use **fictional** `example.test` logins on a **disposable** Vaultwarden server. The user has already successfully synchronized a private account on the actual host; do not copy any account identifiers, hostnames, credential contents, or screenshot labels into repository documentation, logs, or CI artifacts.
- Use a private temporary `XDG_DATA_HOME` and an independently named `PASSFLICK_VAULT` path **that is not the historical vault**, and build the feature-enabled executable through the approved `mbx` workflow. Avoid alternate Cargo targets and scratch build directories.
- Test under the actual login session with `WAYLAND_DISPLAY` set and X11 fallback disabled. The feature-enabled command is `passflick projection picker`; plain `passflick` is still the legacy picker. Verify the Wayland app ID with `hyprctl clients`.
- Verify `wl-copy --help` advertises its long `--sensitive` option before copying; old helpers must fail without copying. Do not use clipboard managers that send fictional test values to a network service.
- Before testing with a disposable server, prove that the preview opens in its locked state with **no snapshot**, and that Escape closes without creating a legacy vault or changing the existing clipboard.

## Verified real host evidence and appearance

**2026-11-08 (Mexico-local session):** The actual EndeavourOS/Hyprland host accepted a feature-enabled native CLI sign-in with its existing private-CA trust, published an encrypted offline projection, and opened a populated picker. The user demonstrated two-field site/account filtering, selection and password/username copy behavior, then installed the same feature-enabled binary with Cargo. A copy of the four projection files was moved from a disposable XDG location to the user's normal XDG data directory without touching the legacy vault. The first permanent-location open required the independent local passphrase; closing and reopening the same picker in the same login session **did not** prompt again. This validates same-session cache reuse on this host, not login/logout lifetime or every compositor environment.

**System appearance:** The host showed legible System **Light** in daytime and System **Dark** later, with an opaque theme-aware panel after a temporary transparency regression was fixed in [`91561c5`](https://github.com/sguzman/passflick/commit/91561c5547256d32744df8623b8711cf1e74b4a3). This verifies both resolved modes and selector usability, **not** an uninterrupted automatic Darkman day→night transition. It does not authorize manual global theme switching, logout or reboot for testing.

**Unverified:** exact sensitive clipboard bytes/history policy with real target compositor, explicit manual lock while a GUI window is open, wrong-then-correct unlock in the same host Wayland window, logout/relogin keyring expiration, offline refresh failure preserving an authenticated snapshot, first-frame latency, and approved reversible default-command migration. A real-account success is not equivalent to a synthetic security-edge acceptance pass. No real names, addresses, server metadata or secrets are stored in this plan.

## Native Wayland input and clipboard

- A populated feature-enabled preview launches as a floating, centered `passflick-projection-preview` window, without moving tiled windows or focusing another workspace. The user confirmed Super+Minus activation and non-disruptive floating placement on the actual host with the device-specific `dftb` rule; first-frame latency remains unmeasured.
- Website search is initially focused; typing filters title and every URI. Ctrl+Space switches to the account filter, retains both query strings, and does not leak URL paths or tokens through row labels.
- The opt-in populated picker now offers **Lock now** and **Ctrl+L** (including with the site search field focused). With *only fictional credentials* and the test projection, activate each while populated; verify the window clears its decrypted entries before the local keyring operation, no clipboard copy occurs even if Enter activated the button, and `projection status` reports a manual lock. Test that an immediate Enter after Ctrl+L cannot copy a password. Confirm an incorrect local passphrase cannot restore entries and a correct explicit local unlock can. If lock fails, the window must state that global lock is unconfirmed and must not passively rehydrate cached entries. This implementation is not yet target-host accepted.
- Arrow Up/Down selects among separately preserved upstream item IDs; identical site/username pairs remain separately selectable and show a safe variant suffix.
- Enter copies **exact fictional password bytes**, including Unicode, leading/trailing whitespace and any trailing newline, and closes. Shift+Enter copies **exact fictional username bytes**, including Unicode, and closes. Fast Shift release in the same frame must not choose the wrong field. Escape closes without modifying clipboard selection.
- Use the real sensitive-capable `wl-copy` and `wl-paste` in the Wayland session; no X11-mode fallback for this test. Check the **actual clipboard history policy** independently because `--sensitive` is an advisory hint, not guaranteed suppression.

## Login TOTP record scope

- A login item may carry an **encrypted TOTP seed** upstream. [Disposable Vaultwarden acceptance run `42271287029`](https://github.com/sguzman/passflick/actions/runs/42271287029) verifies that the server retains a fictional encrypted login TOTP field while Passflick's offline projection excludes its decrypted seed and `otpauth://` URI.
- The preview remains a **password/username picker**, not a TOTP authenticator. Do not describe its ability to sign in with account-level TOTP MFA as support for generating login-item TOTP codes. Continue using a separate authenticator where needed.

## Offline, locking and refresh

- With the disposable Vaultwarden server offline, the most recently verified encrypted snapshot remains readable **only** after the appropriate local unlock; the UI labels its sync age and that offline access may be stale. A corrupt or absent snapshot fails closed.
- In the **locked GUI**, type the independent local passphrase into the masked field and press Enter. A wrong passphrase must not copy, close, or clear a manual-lock denial. A correct local passphrase must restore the authenticated snapshot **without a network request or a copy on that Enter event**; only a new, deliberate Enter should copy the fictional credential. This sequence passed in disposable Xvfb CI; repeat it on the actual Wayland target.
- From a separate CLI process, run `passflick projection lock` while the populated GUI is open; the GUI must stop copying and clear displayed credentials. A failed unlock must not remove manual-lock denial; an explicit correct local unlock restores access.
- Edit a fictional password remotely, then explicitly refresh with `passflick update`. A previously open picker must refuse to copy the unseen changed value even if the upstream ID matches. Server/account identity swaps must not authorize a colliding item ID.
- Test archive/deletion, failed network/TLS/MFA, malformed sync, concurrent update/lock and interrupted write. Failures must preserve the last good encrypted snapshot, with no stale data represented as live server state.
- **CI evidence, not host acceptance:** a disposable Vaultwarden server now verifies wrong master-password rejection, missing private-CA TLS trust, and incorrect account-level TOTP code through the real masked CLI. Each records a fixed failure category without replacing the last good encrypted projection or keywrap; the TOTP test passed on [disposable run 42699029475](https://github.com/sguzman/passflick/actions/runs/42699029475). Repeat only with fictional credentials on the actual Hyprland machine before marking host failure UX accepted. Do not use the owner's real Vaultwarden account for intentional failed MFA or network attacks.
- After an existing fictional projection has synced successfully, deliberately fail an **explicit** `update` with a disposable wrong local passphrase or unavailable server. Verify the picker distinguishes the **failed last attempt** from the unchanged last-good sync time, using a fixed category only. The sidecar `projection.pfrefresh` must be owner-only mode 0600 and contain no server identity, email, password, token, raw response or error text. A subsequent successful update must clear the visible failure; absent or tampered sidecars must not block authenticated offline access or authorize copying. This status flow is not yet accepted on the target Wayland host.
- **Network reachability loss in CI:** [disposable run 42701821937](https://github.com/sguzman/passflick/actions/runs/42701821937) stopped its *isolated* proxy between successful and failed explicit refreshes. The CLI recorded the fixed sync/network category while the encrypted projection, keywrap, device and server identities, and legacy vault remained byte-for-byte unchanged. This is **not** evidence for a connection cut mid-response or for successful behavior on the owner's real Hyprland session. Any further host test must use a fictional account and an isolated disposable server, never disrupt the owner's actual Vaultwarden service.
- **Mid-response HTTPS cutoff in CI:** [disposable run 42709871709](https://github.com/sguzman/passflick/actions/runs/42709871709) additionally verifies that a separate, one-shot localhost TLS fixture sends HTTP 200 headers followed by only part of the advertised sync body and closes the connection. The account-bound read-only transport rejects it as a network error, with previous encrypted snapshot/keywrap bytes untouched. Original session credentials were dropped before this case; a fixed fictional bearer is used. This is *transport-level* evidence, not complete CLI publication-path or target-host acceptance. Never test by interrupting the owner's live Vaultwarden service.
- On **the target host**, record session-keyring behavior after logout/login. This requires an explicitly agreed login-session change; **never log out or reboot automatically** during acceptance. No clipboard contents should be written to disk.
