# Security model

Passflick holds high-value credentials. It is **pre-release** and has not undergone an independent security audit. Real credentials should not be imported until target-host acceptance and security review are complete.

## Encrypted vault

Passflick stores a local, versioned encrypted projection using Argon2id and XChaCha20-Poly1305 authenticated encryption. Argon2 derives key material directly into zeroizing memory rather than an additional unprotected key array. Session keyring, Secret Service, and same-key backup verification also construct validated 32-byte keys in zeroizing storage and zeroize retrieved key material. The authenticated ciphertext is also decrypted in place inside a zeroizing buffer, without a separate unprotected plaintext return allocation. Credential-owned labels, URLs, and usernames are zeroized on record drop; picker label-cache copies are also held in zeroizing storage. These protections do not prove all transient process memory is cleared, including copies made during display rendering or deserialization. It enforces private vault-file permissions (0600), private vault directories (0700), and current-effective-user ownership for active vault files, write locks, and managed backup directories. Unexpected ownership is rejected rather than treating restrictive mode bits alone as sufficient. Both creation/writes and active-vault unlocks reject shared or symlinked immediate vault directories. File opens are nonblocking and reject symlinks and non-regular files before reading, so an unexpected FIFO cannot hold the process waiting for a writer. Regular vault files larger than 64 MiB are rejected from metadata before allocating a read buffer; a second bounded read still catches files that grow after the metadata check. The derived key can be cached in the Linux session keyring, separately for each vault. Session and desktop key-cache identities use the canonical vault parent plus filename, so deleting the primary file for disaster recovery does not change the identity when the parent still exists. Desktop Secret Service integration is optional. A successful passphrase unlock can also proceed for one picker invocation when kernel session caching fails, without persisting any new unencrypted secret. Optional desktop-keyring enrollment does not automatically use a cached session key when an explicit manual lock is present or cannot be checked. Stale cached keys are reauthenticated and fall back to the passphrase; a failed Secret Service store must not clear a manual lock or refresh the kernel cache. CLI maintenance may try a desktop key for that invocation, but does not copy it to the kernel session cache before validating the current vault. Actual Secret Service and kernel-keyring behavior still requires target-host validation.

New vaults require a passphrase between 12 and 1024 characters. Passphrases do not require arbitrary combinations of character classes. Existing vaults remain unlockable with their original passphrases, including shorter values created by earlier versions.

On first launch, the graphical application can create an encrypted vault using masked passphrase and confirmation fields. Passphrase entry buffers are cleared after setup and unlock attempts. The owned picker search text, temporary normalized search query, and lowercase field/sort-key copies use zeroizing storage, and the search text is scrubbed when switching vault projections; this does not prove that egui, other libraries, or the operating system never retain additional copies. The normal picker shows labels and usernames, not passwords; copying requires an explicit key action. Metadata is rendered with terminal escapes, bidirectional controls, and additional invisible Unicode formatting marks replaced visibly; the original username is preserved for exact copying. CLI vault and backup paths, plus top-level error messages and graphical picker notices/errors, use the same display-only sanitization rather than rendering control characters from filenames. The underlying path bytes are retained for filesystem operations. When a credential has no separate title, or its title is itself a recognized URL, the picker and `list` show a safe site authority rather than userinfo, path, query, or fragment, which can carry sensitive tokens. Titles beginning with a non-authority URI scheme such as `data:`, `javascript:`, or `mailto:` show `(local site)` rather than a sensitive payload. Non-web scheme forms containing `://` (including `data://`, `javascript://`, and `file://`) are also masked rather than exposing payload segments as apparent authorities. Ordinary colon-separated titles such as `Data: Science` remain unchanged. URL-only records with a non-authority scheme payload (such as `data:` or `javascript:`) display `(local site)` instead of exposing that payload; ordinary `example.test:8443` and `localhost:3000` host:port values retain useful display labels. The complete original URL remains encrypted in the vault and searchable; URL-only logins on the same host may need a more specific search to distinguish them. URL-shaped titles are detected even with surrounding whitespace. If multiple different stored credentials would produce the same safe site title and username, the picker appends an ordinal variant label (for example, `Variant 1/2`) without exposing the original URL components or passwords; source-identical records do not inflate that count. Variant numbers identify distinct stored records rather than describing their secrets. The picker caches each visited row label between redraws and clears the cache when a fresh vault projection replaces the records; this avoids repeatedly scanning the full vault every frame. Synthetic tests validate invalidation, but target-host keyboard latency remains unmeasured. Discovery also sanitizes filesystem-derived browser profile names before printing to a terminal, without changing their underlying paths. These display reductions are not guarantees that arbitrary imported titles or hostnames contain no secrets.

## Process and clipboard

Before handling vault data, Passflick disables Linux core dumps and ptrace attachment with `RLIMIT_CORE=0` and `PR_SET_DUMPABLE=0`. Startup fails if these safeguards cannot be installed.

Password copying requires `wl-clipboard` 2.3+ and uses `wl-copy --sensitive`, preserving literal whitespace and newlines. Before passing any credential bytes to a clipboard helper, Passflick probes its `--help` output and refuses helpers that do not successfully advertise `--sensitive`; this costs an additional local process invocation per copy. A successful capability probe does not authenticate the executable or guarantee that a clipboard manager honors the hint. The clipboard helper independently rejects embedded NUL values before launching a process, including those originating from malformed older vaults. The capability check requires a documented long-option declaration at the beginning of an indented help line, not merely a mention of `--sensitive` in prose or a similarly named option. Unsupported helpers fail closed before the actual copy invocation, without falling back to an unmarked clipboard write. If a helper advertises support but later fails, Passflick still checks its exit status and refuses to close the picker as though copying succeeded. Synthetic CLI/GUI regression tests verify misleading help-text refusal, exact copy bytes, and unchanged clipboard state on unsupported helpers. A pinned real `wl-clipboard` 2.3.0 binary also passes the nested-Weston byte-exact `--sensitive` clipboard smoke test. **The sensitive hint is advisory**: clipboard managers or other software in the same desktop session may still capture clipboard contents. The application does not claim protection from a compromised user session.

## Data preservation

Explicit stdin streams are bounded to 32 MiB plus one detection byte, including inputs with no EOF. Explicit CSV files exceeding 32 MiB are rejected using file metadata before allocating a large input buffer; the bounded read remains in place if a file grows afterward. Source imports parse and validate the full CSV before changing a source snapshot. The import deduplication index hashes exact site-title/URL/username identities without storing passwords in keys, and zeroizes these metadata copies when parsing completes or fails. Duplicate Unicode usernames and distinct password variants remain distinguishable. Conflicting aliases for the same semantic field (such as both `password` and `pass`) are rejected instead of silently choosing one. A missing username column is also rejected, although individual credentials may legitimately have an empty username value. The snapshot transaction itself independently rejects empty passwords, NUL-containing usernames or passwords, and credentials with no website or title, so future authorized adapters cannot bypass these import safety checks. For future adapters that supply an all-whitespace URL with a valid title, identity matching uses that distinct title rather than collapsing unrelated accounts under a shared blank URL. The original URL bytes are retained, and a synthetic encrypted import/reopen regression confirms both records remain independently searchable. Suspicious bulk reductions require `--allow-shrink`. Established source snapshots with at least ten distinct account identities also reject a replacement having zero non-secret URL-or-title/username overlap, including same-size Edge/Chrome mixups. `--allow-shrink` explicitly overrides both protections. This is a conservative warning, not proof that overlapping imports come from the correct provider. Updates take an exclusive file lock; refreshing an existing source first creates an encrypted rollback snapshot.

`passflick backup` creates a private encrypted snapshot without overwriting previous backups. `passflick verify FILE` authenticates a selected backup with the active vault key without changing either file. These commands require the active vault to be unlocked. Explicit `passflick recover FILE --confirm` instead authenticates the backup using its own passphrase and can atomically reconstruct a missing or corrupted active file. Recovery and same-key restore reject a snapshot that aliases the active vault, including different hard-link filenames, before any destructive operation. The previous primary bytes are preserved as a raw, **not necessarily valid** safety snapshot; the application attempts to establish an explicit session lock, invalidate session credentials, and remove stale desktop credentials. If any of these steps fails, recovery still reports success for the authenticated file replacement but warns that automatic unlocking might remain possible. A fresh-passphrase prompt is promised only after all cache cleanup steps succeed. The graphical picker clears a cached session key only after an authenticated decryption failure, and distinguishes successful, unnecessary, and failed cleanup; it never reports a key was removed when cleanup failed. Filesystem, header, and schema errors do not delete the cached key. CLI maintenance retries an interactive passphrase only if its cached key fails authentication; this fallback does not silently invalidate or overwrite caches, and non-decryption errors remain fatal. `passflick status` validates the current vault using any claimed cached session key before reporting it as unlocked, without modifying vault bytes. It refuses symlinked or non-regular vault filenames instead of reporting a dangling symlink as a missing vault. The backup directory must itself be private; symlinked backup directories are rejected without writing into their targets, and unsafe vault directories are rejected. `passflick restore FILE --confirm` authenticates the selected backup against the current vault key, acquires the write lock, and preserves another encrypted safety backup before replacing the live records. Vault initialization never silently overwrites an existing path.

Encrypted backup files remain portable: read-only verification and authenticated recovery may accept a private regular snapshot file outside the active vault directory, including one held in an otherwise shared directory, provided the snapshot file itself is private and owned by the invoking user. Such a snapshot is authenticated before its contents can affect the active vault; the active vault's private-directory requirement is never waived. Keeping backups in private directories is still recommended for integrity and availability. These checks do not eliminate every possible filesystem race or protect against a compromised session.

## Source boundaries

Explicit file-path CSV imports require a regular file and use a nonblocking open so a named pipe cannot suspend import waiting for a writer. Symlinks to regular exports remain valid; deliberate streams use standard input (`import SOURCE -`). CSV exports from browsers and password managers are **plaintext**. Passflick does not securely erase these source files, so they should not be left in shared or synchronized locations. Native browser profile discovery examines filenames only; it does not decrypt or import stored credentials.

Future native adapters must use authorized local interfaces. CI fixtures contain synthetic credentials rather than production account data.

The Rust workflow also includes a synthetic end-to-end encrypted-recovery CLI smoke test using only fictional credentials, an isolated temporary directory, and a pseudo-terminal for passphrases. The test checks bad-passphrase non-destructiveness, exact ciphertext restoration, a displaced-raw safety snapshot, and subsequent read-only verification. The [Rust CI run on October 11, 2026 UTC](https://github.com/sguzman/passflick/actions/runs/38185127614) passed all 112 unit tests, including read-only cached session authentication for status, selective GUI cache cleanup, zero-overlap source replacement refusal, invisible Unicode and browser-profile display sanitization, URL-component display redaction, zeroizing ciphertext decryption, stale cached-key CLI retry, four-provider synthetic import, authenticated recovery/restore smoke checks, and Clippy. The [separately verified synthetic GUI and pinned real-helper Wayland workflow](https://github.com/sguzman/passflick/actions/runs/38185127615) also passed. CI is not an independent security audit or target-host acceptance.

These safeguards reduce identifiable risks. They do not replace real-world compositor, clipboard, browser-export, and security acceptance.
